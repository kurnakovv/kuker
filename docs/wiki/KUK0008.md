## 💡 Title
Kuk0008ConstructorMappingOrderAnalyzer

## 🆔 Rule ID
KUK0008

## 📝 Description
This rule enforces a consistent order between three related things in a class:

1) Instance field declarations.
2) Constructor parameters.
3) Assignments from constructor parameters to fields inside the constructor body.

Only fields that are directly initialized from a constructor parameter using simple assignments (for example `_name = name;`) are considered. If the order of constructor parameters and/or the order of the corresponding field assignments does not match the declaration order of the fields they initialize, a diagnostic is reported.

## ⚙️ Configuration

You can configure the severity of the rule via `.editorconfig`.
```.editorconfig
[*.cs]
dotnet_diagnostic.KUK0008.severity = warning # Inconsistent order between field declarations, constructor parameters and assignments | https://github.com/kurnakovv/kuker/wiki/KUK0008
```

## ❔ Why this is a problem
When field declaration order, constructor parameter order, and assignment order all differ, it becomes harder to scan and review a class - especially one with several parameters of similar or identical types (for example, multiple `string`/`int` parameters). Mismatched ordering is a common source of subtle bugs (arguments swapped by mistake) and makes it harder to resolve git conflicts. Keeping a single, predictable order across all three makes classes easier to read and diffs easier to follow.

## 💻 Example

```cs
// ❌ KUK0008: parameter and assignment order does not match field declaration order
class User
{
    private readonly Guid _id;
    private readonly string _name;
    private readonly int _age;

    public User(string name, Guid id, int age)
    {
        _name = name;
        _id = id;
        _age = age;
    }
}

// ✅ OK
class User
{
    private readonly Guid _id;
    private readonly string _name;
    private readonly int _age;

    public User(Guid id, string name, int age)
    {
        _id = id;
        _name = name;
        _age = age;
    }
}
```

## 🗒️ Notes
* Matching | A field is only considered "tied" to a parameter through a simple, predictable assignment such as `_field = parameter;`, matched by name (for example `_name` from `name`). No attempt is made to infer semantic intent from complex or ambiguous expressions - this avoids false positives.

    ```cs
    // ✅ Not analyzed: assignment is not a simple parameter-to-field assignment
    _name = name.Trim();
    ```

* Out-of-scope fields | Fields that are not directly initialized from a constructor parameter are ignored and do not affect the ordering check.

    ```cs
    // ✅ OK: _createdAt is not tied to a constructor parameter, so it is ignored
    class User
    {
        private readonly DateTime _createdAt;
        private readonly Guid _id;
        private readonly string _name;

        public User(Guid id, string name)
        {
            _id = id;
            _name = name;
            _createdAt = DateTime.UtcNow;
        }
    }
    ```

* Multiple assignments to the same field | If the same field is assigned more than once from a parameter in the constructor body, there is no single, unambiguous mapping between that field and a parameter, so the constructor is skipped entirely and no diagnostic is reported.

    ```cs
    // ✅ Not analyzed: _a is assigned twice, so the mapping is ambiguous
    _a = a;
    _b = b;
    _a = b;
    ```

* Advanced constructs | `base(...)` and `this(...)` constructor initializers and primary constructors are not supported by this rule.

* Partial classes | For simplicity, only fields declared in the same partial type declaration (the same `{ }` block) as the constructor are considered. Fields declared in a different partial declaration of the class - whether in the same file or another file - are ignored, since establishing a single, well-defined declaration order across separate partial declarations would be complex.

    ```cs
    // ✅ OK
    public partial class User
    {
        private readonly int _age;
        private readonly string _name;
    }

    public partial class User
    {
        private readonly Guid _id;

        public User(string name, int age, Guid id)
        {
            _id = id;
            _name = name;
            _age = age;
        }
    }
    ```

* Layout-sensitive types | `struct` types (which use sequential layout by default), and classes or structs explicitly marked with `[StructLayout(LayoutKind.Sequential)]` or `[StructLayout(LayoutKind.Explicit)]`, are not analyzed. For these types the field declaration order (or explicit offsets) determines the in-memory layout, which can matter for interop (P/Invoke, marshaling) or persisted binary data. Reordering fields for such types could silently change their memory layout and break compatibility, so they are excluded from this rule entirely.

    ```cs
    // ✅ Not analyzed: struct layout depends on field declaration order
    public struct Point
    {
        private readonly int _x;
        private readonly int _y;

        public Point(int x, int y)
        {
            _y = y;
            _x = x;
        }
    }
    ```
